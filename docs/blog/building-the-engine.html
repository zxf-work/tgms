Nine wrong bottlenecks:
building our storage engine

Xiaofei Zhang · University of Memphis · July 2026 · report · code

Kùzu — the embedded graph engine under one of our storage backends — was acquired, and its open-source line ended. We replaced it and DuckDB with an engine built for our semantics: ~7,500 lines of Rust behind an unchanged Python interface, validated by a 500-case oracle the implementation was never allowed to touch.

One property pays for everything

Segments are immutable. The only mutation in the model — closing a version's transaction time — is an append-only patch folded in by compaction. Everything expensive elsewhere becomes free here: snapshot isolation is "pin a manifest", mmap is safe because bytes never change, a checksum verified once stays verified, the segment cache cannot go stale, readers never lock.

We never tuned our way to correctness. Immutability made the correct thing the cheap thing.

Compression chosen by trial, not by policy

The writer trial-encodes every column and keeps whichever representation is smaller. Sorted timestamps and near-constant columns collapse; hash-derived ids stay raw by measurement, not by special case.

That last row is the one we would frame: we parallelized materialization, measured nothing, and a fifteen-minute stage probe showed the fast path was unreachable on any store containing corrections — which is every real store. The fix (merge by overlap clusters) made the "irrelevant" parallel code the thing doing the work:

The transferable rule. The named, algorithmic-looking component is rarely the cost — it is the part everyone already thought about. The scan call around it, the boundary crossing per row, the validator per call, the manifest per commit: that is where milliseconds live. Re-measure before writing the commit message; if the number did not move, the hypothesis was wrong even though the code got better.

What we refused to optimize

Durability. A commit is several fsyncs and ~20 ms, so batch-1 writes are slow and batch-1000 writes hit 46k events/s on the same floor. The lever is group-commit at the API — never weakening what a commit means. And a fifteen-minute probe priced the next "obvious" win (passing ids as integers across the language boundary) at 0.94 ms of a 32 ms operator — measured, declined, recorded. The measurement that stops you is worth as much as the one that redirects you.
