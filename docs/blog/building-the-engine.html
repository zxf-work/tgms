Post #6 · Native engine

Nine wrong bottlenecks:
building our storage engine

Xiaofei Zhang · University of Memphis · July 2026 · report · code

When Kùzu — the embedded graph database under one of our two storage backends — was acquired and its open-source line ended, we had a choice: find another general-purpose engine to sit under TGMS, or build the storage layer the semantics actually wanted. We built it: about 7,500 lines of Rust behind an unchanged Python adapter interface, validated against a 500-case brute-force oracle that the implementation was never allowed to touch.

This post is not about the design being clever. It is about the log we kept while building it, because the log's headline is embarrassing and useful: nine times we identified "the bottleneck" and were wrong nine times.

The misdiagnosis table

We kept a running table (it lives in engine_lessons.md) with three columns: what we believed, what we measured, what the cost actually was. A few entries:

  • We believed a Rust scan would beat NumPy. It measured 2–5× slower — a column resolved by name and a table walked per row, inside the loop.
  • We believed diff_snapshots was scan-bound. The two scans were 54 ms of 419; a lookup that fetched sixteen rows was rebuilding the entire store to find them.
  • We believed a point lookup was all storage. Argument validation cost as much as reading the data — a JSON-schema validator was being recompiled on every call.
  • We believed 10M-row scans were materialize-bound, parallelized materialization, and moved the number from 811 ms to 819. A stage probe then showed the parallel path never executed: one overlapping correction segment voided the fast path's all-or-nothing check, and a corrected store is the normal store.

Three of the nine fixes were correct but irrelevant — good code, kept, that produced none of the win attributed to it. The discipline that survived: re-measure before writing the commit message. If the number did not move, the hypothesis was wrong even though the code got better.

What the design actually bought

One property does most of the work: segments are immutable. The only mutation in the model — closing a version's transaction time — is an append-only patch folded in by compaction. Immutability makes snapshot isolation, safe mmap, verify-once checksums, a sound segment cache, and lock-free readers free rather than engineered.

On top of that: valid-time clustering (so scans read in output order and merges are usually concatenations), derived identity (edge ids are hashes, never stored twice), frame-of-reference compression chosen per column by trial (the writer keeps whichever representation is smaller — sha256-derived columns stay raw by measurement, not by special case), and a packed string heap. Segments landed at 24.6 bytes per edge version — smaller than a mature lz4 columnar engine holding the same rows.

The lesson we would give anyone

"We rewrote it in Rust" is not a performance claim, and the named, algorithmic-looking component is rarely the cost — it is the part everyone already thought about. The scan call around it, the boundary crossing per row, the validator per call, the manifest per commit: that is where the milliseconds live. Profile the layer before optimizing it, and price the optimization you are about to decline — one fifteen-minute probe saved us an hour of plausible work by putting a number (0.94 ms of a 32 ms operator) on the next "obvious" improvement.
